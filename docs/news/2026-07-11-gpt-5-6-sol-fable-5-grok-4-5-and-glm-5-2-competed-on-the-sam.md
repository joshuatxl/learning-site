# GPT-5.6 Sol, Fable 5, Grok 4.5 and GLM 5.2 competed on the same math

<p>In ~8 mins: the trap-filled prompt all four had to survive, the 2.667x defect hiding in the cheapest model, a 255x compute cut with a memory bill nobody prices, and who should actually care.</p><p>All live HTML demos are down below with guide how to use it in Appendix.</p><p>Most teams pick an open model to save money, then trust it to build the tooling that measures their real spend. We handed that exact job to four frontier models and checked the arithmetic by hand. This is the 5 stage field test that found one silent defect hiding in the cheapest option.</p><p>We gave GPT-5.6 Sol, Fable 5, Grok 4.5, and GLM 5.2 one prompt. Build a self contained KV-cache debugger in a single HTML file, with exact formulas, five named presets, a full testing API, and eleven objective checks written to trip a model that fakes the physics.</p><p>Then we called each tool’s public API directly and compared every output against an independent reference. No vibes, no leaderboard. Just whether the numbers were right.</p><p><em><strong>The four KV-cache debuggers running side by side, one per model. Every tool is live as HTML in the Sources section below, open any of them in your browser.</strong></em></p><h2><strong>Stage 1: We tested the physics</strong></h2><p>A KV cache is the memory a transformer keeps so it does not recompute every earlier token on every new one. Get the formula wrong and your memory math and your compute math both drift quietly in production.</p><p>So the prompt fixed the physics in advance. Cache memory scales with KV head count and includes a factor of 2 for keys and values. Attention work scales with query head count. Cached decode work grows linearly with sequence length per step, uncached work grows quadratically. Sequence length at generated step t is <em><strong>prompt_tokens + t</strong></em>, so the first token sits at prompt length plus one, never at prompt length.</p><p>Several of those checks were traps. Merge keys and values and lose the factor of 2, use query heads for memory instead of KV heads, treat step 1 as prompt length, hold cached work constant across steps. Any one of them silently doubles or halves a headline number.</p><p><strong>The test rewarded correct arithmetic under adversarial instructions.</strong></p><h2><strong>Stage 2: On the core math, all four tied</strong></h2><p>Under the default configuration, every model returned identical exact integers.</p><p>The default 2048 prompt tokens, 256 generated, 32 layers, 32 query heads, 32 KV heads, 128 head dimension, BF16.</p><p>None of the four merged keys and values. None used query heads for memory.</p><p>All used BigInt for exact integer arithmetic and returned exact decimal strings through the testing API rather than rounded floats. Every trap the prompt set for the formulas went unsprung.</p><p>Across 256 steps, cached work per step rises only about 12%, because it grows linearly with sequence length.</p><p>Uncached work per step rises faster and keeps curving, because it grows with the square. Every model had to encode that difference, and every one did, which is why the 255x gap holds instead of drifting as the sequence gets longer.</p><h2><strong>Stage 3: KV caching bought a 255x compute cut and a memory bill nobody prices</strong></h2><p>The interesting number is what caching actually saves, and what it costs. On the default config the tools agreed exactly, which is the point. The mechanism is stable and you can plan around it.</p><p>Cached decoding runs about 255 times less attention work than recomputing the full sequence each step, a 99.6% reduction. That is the entire reason autoregressive generation is affordable.</p><p>The bill for that cut is memory. The cache climbs 524,288 bytes per token and lands at 1.125 GiB for one request at these settings, and it grows linearly with sequence length while the compute saving grows super linearly. Longer context makes the trade better on compute and worse on memory at the same time.</p><p>The lever is KV head count. The same model, same math, at three different KV head counts:</p><p>The compute stays flat because attention work rides on query heads, not KV heads.</p><p>The batched serving preset, 16 requests at once with grouped query attention, lands at exactly 4.5 GiB of cache. The long context preset, a single 16K prompt over 48 layers, reaches 3.1875 GiB on its own. Scale changes the picture fast. Batch multiplies the bill linearly, and every layer you add multiplies it again, which is why serving cost is a memory ceiling problem long before it is a compute one.</p><h2><strong>Stage 4: GLM 5.2 shipped a preset that is off by 2.667x</strong></h2><p>Here the tie breaks:</p><p>GLM 5.2 has a real math defect, and it is the kind you would never catch by glancing at the tool.</p><p>Its Small MHA preset ships <em><strong>numLayers:32</strong></em>. The spec, and the other three models, ship <em><strong>numLayers:12. </strong></em>Every cache memory and attention figure for that preset is scaled by 32/12, which is 2.667x. Select the preset, read the number, plan against it, and you are off by more than double with no warning.</p><p>We confirmed this straight from the source, not from behavior. The other four GLM presets are correct, which makes this worse, since four right answers train you to trust the fifth.</p><pre>// GLM 5.2 Small MHA preset (from source)
&quot;Small MHA&quot;: { promptTokens:512, generatedTokens:128, batchSize:1,
               numLayers:32, ... }   // spec requires numLayers:12

// Fable 5 / GPT-5.6 Sol / Grok 4.5, same preset
&quot;Small MHA&quot;: { ..., numLayers:12, ... }   // correct</pre><p>GLM has a second, quieter gap. Its API validates query and KV head counts against the allowed lists but never checks head dimension, so <em><strong>setConfig({ headDimension: 8 })</strong></em> slips through. That one does not corrupt a formula, but it is a hole where the others hold.</p><h2><strong>Stage 5: The split that actually decides which model you trust</strong></h2><p>Strip out the tie and one axis explains the whole result. How each model treats its own testing API versus its UI.</p><p>GPT-5.6 Sol is the strict one. Its <em><strong>validateConfig()</strong></em> throws typed RangeError exceptions for every bad input, rejects head counts and head dimensions outside the allowed lists, and preserves the last valid config after a rejected call. Feed it an out of spec value through the API and it refuses, cleanly.</p><p>Fable 5 and Grok 4.5 make the opposite call on purpose. Both keep strict validation in the UI and deliberately relax it in the API so arbitrary formula verification configs can be driven by code. Fable’s own source comment says so outright. This is a design decision for testability, not a bug, and both still enforce the structural rules that keep the math valid, KV heads never exceed query heads, query heads stay divisible by KV heads.</p><p>GLM 5.2 lands in between, and not by design. It gates head counts but forgets head dimension, so it is stricter than Fable and Grok on one axis and leakier than Sol on another, without a stated rationale for either.</p><h2><strong>One honest caveat: what this test did not measure</strong></h2><p>Before anyone reads a winner into this, here is what the field test did not touch.</p><p>We measured output correctness only. Cost, token usage and generation time were not recorded, so this says nothing about which model is cheaper or faster to run the task. Interface accessibility, mobile behavior, and cross browser support were out of scope too.</p><p>The prompt also carried a genuine contradiction. Three required test cases asked for a query head count of 4 and a head dimension of 8, both below the allowed lists the same prompt declared. A strictly compliant tool cannot run them without breaking its own rules. Sol rejected them, Fable and Grok accepted them through the API, GLM split the difference. So how a model handled those three cases reflects how it resolves contradictory instructions, not whether it can do the math. We verified the formulas with a clean replacement config all four compute correctly.</p><h2><strong>Common mistakes this test exposes in how teams pick a model</strong></h2><ul><p>Trusting a preset because the tool looks finished. GLM’s Small MHA is off by 2.667x and the UI gives no hint.</p><p>Reading a leaderboard number as a correctness guarantee. All four tie on headline math and still diverge on validation and presets.</p><p>Assuming an open model is riskier only on capability. GLM’s arithmetic was fine, its constant was not.</p><p>Treating API acceptance of odd inputs as a bug. For Fable and Grok it is a documented testability choice, not a failure.</p><p>Validating one input class and calling it done. GLM checks head counts, forgets head dimension, and that is where inputs leak.</p><p>Judging a model on prompt cases that contradict the prompt’s own rules. That measures instruction handling not math.</p><p>Skipping the API path in your own eval. UI validation and API validation diverge in three of four models here.</p></ul><h3><strong>The bottom line</strong></h3><p><strong>All four frontier models nailed the transformer arithmetic, so the real differences live in presets and validation, where the cheapest model was the only one carrying a silent 2.667x error.</strong></p><p>Tonight, take whatever internal calculator or config tool you rely on and call its API with one deliberately out of spec value, then check whether the number that comes back is right or just confident. That single call is the whole test.</p><p>Save this for the next time a benchmark tells you two models are tied. Bookmark it, because tied on headline numbers and equal in production are not the same claim.</p><h2><strong>Sources</strong></h2><h3><strong>The four tools (live HTML, open in any browser)</strong></h3><p><strong>1. Nothing to install. Open any of the four links in Sources and the whole tool loads in the browser.</p><p>The tool models two things only: KV-cache memory and attention score multiplications. It does not simulate a full transformer, so there are no projections, MLP, softmax, or measured latency. Every number on screen is exact, computed with BigInt, not estimated.</p><ol><p>Set a config in the left panel. Prompt tokens, generated tokens, batch size, transformer layers, query heads, KV heads, head dimension, and data type. The memory and attention panels update live.</p><p>Watch the timeline. It shows prefill running once over the prompt, then cached decoding one token at a time. Sequence length is prompt <strong>tokens + t</strong> at step <em><strong>t.</strong></em></p><p>Read the memory panel. Growth per token is constant, final cache grows linearly with sequence length. Drop KV heads to see GQA and MQA shrink memory while attention work stays flat.</p><p>Read the attention panel. Cached work grows linearly, uncached grows with the square. The reduction ratio is the whole case for caching.</p><p>Load the presets. Small MHA, 7B-style GQA, Long-context GQA, Batched serving, MQA comparison. This is where the GLM defect lives: its Small MHA preset loads 32 transformer layers instead of the spec’s 12, so every number for that preset is 2.667x too high.</p></ol><p>Every tool exposes a testing API on the page. Open the browser console and call it directly, for example <em><strong>window.kvCacheDebugger</strong></em> with a config object, to get exact integer strings back. That is how we drove all four with identical inputs and compared outputs against an independent reference, rather than trusting the on screen UI. Feed each one an out of spec value through the API to see the validation split; Sol throws, Fable and Grok accept by design, GLM checks head counts but not head dimension.</p><p><strong>The fastest way to see the defect</strong></p><p>Open the GLM link and the Fable link side by side. Select Small MHA in both. Compare the transformer layer count. GLM reads 32, Fable reads 12. Everything downstream of that follows.</p><h2><strong>Questions</strong></h2><p><strong>Is GLM 5.2 broken?</strong></p><p>No. Its core arithmetic is correct. One preset ships the wrong layer count (32 instead of 12), which scales that preset’s numbers by 2.667x. The other four presets are fine.</p><p><strong>Does this mean open models are worse?</strong></p><p>Not from this test. The defect was a single constant, not a capability gap. GLM did the hard math correctly. The lesson is to test presets and the API path, not to avoid open models.</p><p><strong>Which model won?</strong></p><p>None outright. All four tie on core arithmetic. Sol is strictest on validation, Fable and Grok relax the API on purpose for testability, and GLM is the only one with a real preset defect.</p><p><strong>What is the 2.667x from?</strong></p><p>32 divided by 12. GLM’s Small MHA preset uses 32 transformer layers where the spec uses 12, and cache and attention figures scale linearly with layer count.</p><p><strong>Did you measure cost or speed?</strong></p><p>No. This test measured output correctness only. Cost, tokens, and latency were not recorded, so it makes no claim about which model is cheaper or faster to run.</p>
