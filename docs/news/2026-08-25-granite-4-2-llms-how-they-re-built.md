# Granite 4.2 LLMs: How They're Built

<h2><a href="https://huggingface.co/blog/ibm-granite/granite-4-2#granite-42-llms-how-theyre-built"> </a> Granite 4.2 LLMs: How They&#x27;re Built</h2><p><em>A technical walkthrough of how we built the Granite 4.2 reasoning model family.</em></p><p><strong>Authors:</strong> Granite Team, IBM</p><p><strong>TL;DR:</strong> Granite 4.2 is our first family of dense, decoder-only reasoning LLMs, released in three sizes: <strong>3B, 8B, and 30B</strong>. Each model is pre-trained from scratch on roughly 15T tokens with a five-phase strategy that extends the context window to 512K tokens, supervised fine-tuned on chain-of-thought, reasoning, and agentic-trajectory data, then post-trained with a <strong>multi-stage reinforcement learning pipeline</strong>. That pipeline includes agentic RL, where the 8B and 30B models learn to act with tools inside real sandboxed environments. Every model has a <strong>thinking / non-thinking</strong> switch, a <strong>low-effort</strong> thinking mode that spends a short reasoning budget on easy questions, and native tool calling. All Granite 4.2 models are released under the Apache 2.0 license.</p><p><strong>Links:</strong></p><ul><li><a href="https://huggingface.co/collections/ibm-granite/granite-42-language-models">Granite 4.2 HF Collection</a></li><li><a href="https://github.com/ibm-granite/granite-4.2-language-models">GitHub Repository</a></li><li><a href="https://www.ibm.com/granite/docs/">Granite Docs</a></li></ul><h2><a href="https://huggingface.co/blog/ibm-granite/granite-4-2#overview"> </a> Overview</h2><p>Granite 4.2 is the reasoning-focused release of the Granite language-model family. Earlier Granite releases were strong instruction-following assistants; Granite 4.2 adds explicit reasoning. Every model can produce a chain of thought before its answer and can run in <strong>thinking</strong> or <strong>non-thinking</strong> mode depending on how much deliberation a task needs. A <strong>low-effort</strong> mode falls between the two, spending a short reasoning budget on easy questions.</p><p>The three sizes (<strong>3B, 8B, and 30B</strong>) share the same architectural design and follow the same training pipeline (pre-training from scratch, SFT, then multi-stage RL), each at its own scale. All three are strong reasoners and instruction followers. The clearest capability split shows up in post-training. The <strong>8B and 30B</strong> models additionally go through an <strong>agentic RL</strong> block that teaches them to operate as agents: calling tools, editing and running code, driving a terminal, and searching the web inside real environments. Every model supports native tool calling. Served through an OpenAI-compatible endpoint (for example, with vLLM), it emits tool calls in the OpenAI function-calling format and plugs into agentic harnesses without extra glue. Granite 4.2 is also supported in SGLang, see the <a href="https://docs.sglang.io/cookbook/autoregressive/IBM/Granite-4.2">SGLang cookbook</a> for a ready-to-serve recipe.</p><p>The rest of this post walks through the build: architecture, pre-training, supervised fine-tuning, the multi-stage RL pipeline, and results.</p><h2><a href="https://huggingface.co/blog/ibm-granite/granite-4-2#model-architecture"> </a> Model Architecture</h2><p>Granite 4.2 models are built on a decoder-only dense transformer architecture with the following core components:</p><ul><li><strong>Attention:</strong> Grouped Query Attention (GQA) with 40 attention heads and 8 KV heads</li><li><strong>Position Embedding:</strong> Rotary Position Embedding (RoPE) with θ = 10,000,000</li><li><strong>Feed-Forward:</strong> MLP with SwiGLU activation</li><li><strong>Normalization:</strong> RMSNorm (ε = 1e-5)</li><li><strong>Embeddings:</strong> Separate input/output embeddings (not tied)</li><li><strong>Precision:</strong> bfloat16</li></ul><h2><a href="https://huggingface.co/blog/ibm-granite/granite-4-2#pre-training"> </a> Pre-Training</h2><p>Granite 4.2 is trained from scratch on approximately <strong>15 trillion tokens</strong> using a five-phase training strategy. Phases 1–2 focus on foundational pre-training, phases 3–4 perform mid-training with progressively higher-quality data annealing, and phase 5 introduces long-context training, extending the context window to <strong>512K tokens</strong>. Each phase uses a distinct data mixture and learning-rate schedule, gradually shifting from broad web-scale data toward more curated, high-quality sources.</p><p>The pre-training recipe closely follows the previous generation; for a detailed treatment of the data blend, phase schedule, and long-context extension, see the <a href="https://huggingface.co/blog/ibm-granite/granite-4-1">Granite 4.1 blog</a>.</p><h2><a href="https://huggingface.co/blog/ibm-granite/granite-4-2#sft-data-preparation--quality-control"> </a> SFT: Data Preparation &amp; Quality Control</h2><p>Supervised fine-tuning (SFT) turns the base model into a reliable instruction-following, reasoning, and tool-using assistant. The SFT data mixture combines agentic (31.6%) and non-agentic (68.4%) data, totaling approximately 7.2 million samples, or roughly 100B tokens, of which about 65B are trainable.</p><p>The <strong>agentic corpus</strong> covers a broad range of domains, including software engineering (SWE, 69%), tool calling (12.1%), terminal use (8.0%), math (3.5%), search (0.8%), and action (0.2%). These samples and trajectories are generated using a diverse set of agent scaffolds and harnesses, including OpenHands, OpenCode, Terminus-2, SWE-agent, OpenResearcher, MiniSWE, OpenSeeker, EnvScaler, Gemini CLI, Hermes, Codex, and Goose. The agentic data combines samples from both open-source datasets and our own synthetically generated RL environments, spanning a variety of agent–harness combinations.</p><p>The <strong>non-agentic corpus</strong> consists of several major categories: instruction following (18.8%), coding (18.8%), math (14.6%), multilingual (7.0%), science (5.4%), reasoning (3.0%), and safety (0.8%).</p><h3><a href="https://huggingface.co/blog/ibm-granite/granite-4-2#data-quality-control"> </a> Data Quality Control</h3><p>We apply multiple stages of quality control before a sample enters the final SFT mixture. First, data from different sources is normalized and reformatted into a consistent OpenAI Chat format, making the conversation structure and tool interactions uniform across datasets and scaffolds.</p><p>We then use GPT-OSS-120B and Gemma 4 as LLM-based judges to assess sample quality. Low-scoring samples are removed, as are samples containing hallucinated or fabricated information, invalid tool interactions, or tool calls to functions that are not defined in the corresponding tool list. Several targeted, dataset-specific heuristic rules are also applied where appropriate to further improve quality and remove known sources of noise.</p><p>Finally, we perform both local and global deduplication. Deduplication is based on SHA-256 hashes computed over the combination of the <code>tools</code> and <code>messages</code> fields, removing duplicate samples both within individual data sources and across the overall SFT mixture.</p><h3><a href="https://huggingface.co/blog/ibm-granite/granite-4-2#sft-training-details"> </a> SFT Training Details</h3><p>The complete corpus is first globally shuffled to reduce ordering effects and ensure that samples from different domains are well mixed during training. The shuffled corpus is then partitioned into equally sized <code>.parquet</code> shards, which are tokenized using the model&#x27;s tokenizer and chat template and prepared for large-scale distributed training.</p><p>Before launching the final large-scale runs, we tune hyperparameters on representative configurations, sweeping learning-rate schedules, initial learning rates, and warm-up ratios to find settings that train stably across model sizes. The final training configuration is summarized below:</p><h3><a href="https://huggingface.co/blog/ibm-granite/granite-4-2#phase-2-sft-for-the-30b-model"> </a> Phase 2 SFT for the 30B Model</h3><p>For the 30B model, we additionally perform a second phase of SFT focused specifically on agentic coding. In this phase, agentic, SWE, and coding data are upsampled to increase their effective contribution to the training distribution, while approximately 16% of the mixture is retained as replay data from the original SFT corpus.</p><p>The 30B model is then fine-tuned for roughly one additional epoch at a lower learning rate of 3.0e-6. This targeted second phase increases the model&#x27;s exposure to agentic coding trajectories without discarding the capabilities acquired during the initial SFT phase.</p><h2><a href="https://huggingface.co/blog/ibm-granite/granite-4-2#reinforcement-learning-a-multi-stage-multi-environment-pipeline"> </a> Reinforcement Learning: A Multi-Stage, Multi-Environment Pipeline</h2><p>After SFT, we apply a <strong>multi-stage, multi-environment reinforcement learning pipeline</strong>. Rather than a single RL pass, we run a <em>chain</em> of focused stages spanning many environments: math, code, science, instruction following, tool use, and structured output, then software engineering, terminal use, and web search. Each stage is an independent RL run that targets one capability and warm-starts from the previous stage&#x27;s checkpoint.</p><p><em>Figure 1. The staged RL curriculum. Foundational RL (verifiable rewards + skill boosters) runs for all sizes; the agentic RL block (SWE → Terminal → Search) runs for 8B and 30B only. Every model finishes with RLHF. Each stage is a separate GRPO run that warm-starts from the previous checkpoint.</em></p><h3><a href="https://huggingface.co/blog/ibm-granite/granite-4-2#training-methodology"> </a> Training Methodology</h3><p>Every stage trains with <strong>asynchronous GRPO</strong> (<a href="https://arxiv.org/abs/2402.03300">Group Relative Policy Optimization</a>), so the generator and trainer halves of the loop never block on each other. A pool of generation workers keeps sampling responses and dropping the finished trajectories into a shared buffer; once the buffer holds a full step&#x27;s worth, the trainer pulls that batch, takes an optimizer step, and streams the updated parameters back to the generator workers without pausing them. A refresh can land partway through a rollout, leaving a single trajectory stitched together from two adjacent policy versions. We allow this instead of paying to prevent it: the workers reuse their existing KV cache rather than rebuilding it after each refresh, and the one guardrail is a limit that keeps them from drifting more than a single update behind the trainer, which bounds how off-policy any sample can get. Whatever mismatch survives that limit is handled in the objective by <em>truncated importance sampling</em>, which clamps the train-versus-generation log-probability ratio to a fixed ceiling so a handful of stale tokens cannot dominate an update.</p><p>Advantages are group-relative with a <strong>leave-one-out baseline</strong>: each response is judged against the mean reward of the <em>other</em> samples drawn for the same prompt, which removes the need for a separate value network. To make this concrete, take <strong>RLVR</strong>, the first and longest-running stage: each step pairs <strong>256 prompts</strong> with <strong>16 sampled responses apiece</strong> for a <strong>4,096</strong>-example batch, which the trainer consumes in a single optimizer step before the next rollout begins. Later stages keep this machinery unchanged and adjust only the per-stage shape, shown next.</p><h3><a href="https://huggingface.co/blog/ibm-granite/granite-4-2#rl-training-configuration"> </a> RL training configuration</h3><p>The pipeline keeps a common backbone of hyperparameters across every stage, which makes the curriculum easier to run and compare. A handful of knobs are fixed everywhere:</p><p>What changes from stage to stage is the <em>shape</em> of each run: how many prompts and generations per step, how long the context is, whether the agent loop runs, and how hard we pull back toward the reference policy. The table below gives the exact settings for the <strong>30B</strong> chain, stage by stage:</p><p><em>Parameters shown for the 30B model. Global batch size = prompts/step × generations/prompt (e.g. 256 × 16 = 4096 for RLVR). The 3B and 8B models use the same recipe and hyperparameters with <strong>fewer stages</strong> (see <a href="https://huggingface.co/blog/ibm-granite/granite-4-2#how-the-three-sizes-differ">How the Three Sizes Differ</a>); the stage list is what changes, not the knobs.</em></p><p>The <strong>KL schedule</strong> follows the reward type: explore freely where the reward is objective and verifiable (RLVR and SWE 2 run at KL 0), and stay close to the reference where the objective is preference, safety, or a narrow skill graft (RLHF and the code booster use KL 0.05). The <strong>rollout-turns</strong> column counts the environment interactions <em>GRPO itself</em> sees per rollout. In every case the model is trained on complete, real-environment trajectories.</p><h3><a href="https://huggingface.co/blog/ibm-granite/granite-4-2#the-staged-curriculum"> </a> The Staged Curriculum</h3><p>Each stage is a separate RL run with a single objective and its own reward signal. When it finishes, its policy is exported to Hugging Face format and becomes the base model for the next stage, so the pipeline is a sequence of warm-starts:</p><pre>SFT ─▶ RLVR ─▶ Skill boosters ─▶ SWE agent ─▶ Terminal ─▶ Search ─▶ RLHF
      └──────── foundational RL ────────┘   └──────── agentic RL (8B / 30B) ────────┘</pre><p>The <strong>8B and 30B</strong> models follow the full ladder. The <strong>3B</strong> model takes a shortened path: foundational RL and alignment, without the agentic block.</p><h3><a href="https://huggingface.co/blog/ibm-granite/granite-4-2#reward-signals"> </a> Reward Signals</h3><p>A stage is defined mostly by <em>how it is rewarded</em>. Across the pipeline there are three reward types, and a single stage can use more than one:</p><p>Verifiable rewards are objective and hard to game, so the pipeline front-loads them. Judge- and preference-based rewards handle open-ended qualities that no checker can express. Agentic-outcome rewards are the sparsest: often a single bit at the end of a long tool-use trajectory.</p><h3><a href="https://huggingface.co/blog/ibm-granite/granite-4-2#foundational-rl-build-the-skills"> </a> Foundational RL: Build the Skills</h3><h3><a href="https://huggingface.co/blog/ibm-granite/granite-4-2#rlvr-verifiable-reward-rl"> </a> RLVR: verifiable-reward RL</h3><p>RLVR is the foundational stage and the broadest data mix in the pipeline: a single blended dataset spanning many verifiable domains.</p><ul><li><strong>Math:</strong> chain-of-thought with boxed-answer checking, plus formal proving in <strong>Lean</strong></li><li><strong>Competitive coding:</strong> solutions checked against hidden tests in a sandbox</li><li><strong>STEM / graduate-level science MCQA</strong> and general knowledge</li><li><strong>Instruction following:</strong> structured-output and inverse-instruction tasks</li><li><strong>Tool / function calling:</strong> single-step tool use</li><li><strong>Reasoning puzzles</strong> and <strong>abstention</strong> (knowing when to refuse)</li></ul><p>Each task type carries its own verifier, so the reward is grounded per example. RLVR runs for <strong>two rounds on 3B and 8B, and three on 30B</strong>. Each round is a fresh warm-started run on a re-weighted mix of public and internally curated RL data.</p><h3><a href="https://huggingface.co/blog/ibm-granite/granite-4-2#skill-boosters-targeted-lifts"> </a> Skill boosters: targeted lifts</h3><p>After RLVR, a few short <strong>booster</strong> stages sharpen specific capabilities that benefit from concentrated training focusing on the following domains:</p><ul><li><strong>Instruction following (IF):</strong> multi-turn chat, inverse-IFEval, structured outputs</li><li><strong>Code:</strong> competitive coding only</li></ul><p>Boosters are small, focused runs. A light KL penalty keeps the model close to its current behavior while nudging one skill.</p><h3><a href="https://huggingface.co/blog/ibm-granite/granite-4-2#agentic-rl-learning-to-act-8b--30b"> </a> Agentic RL: Learning to Act (8B / 30B)</h3><p>In the agentic stages the model learns to <strong>act</strong>: call tools, observe results, and iterate inside a real environment, rewarded on whether the task was actually solved. These stages share the same shape: multi-turn tool use, real (not simulated) environments, sparse outcome rewards, and GRPO, warm-started from the coding-boosted checkpoint. They run in order: <strong>SWE → Terminal → Search</strong>.</p><p><em>Figure 2. The three agentic-RL environments. Each pairs a real harness with a real environment and a sparse, outcome-based reward. The 3B model runs none of these.</em></p><ul><li><strong>SWE agent (software engineering).</strong> Each task is a real repository in its own sandbox. Driven by the <a href="https://github.com/All-Hands-AI/OpenHands">OpenHands</a> harness, the model reads code, edits files, and runs the test suite over many internal turns. The reward is verifiable: do the hidden tests pass? Tasks are drawn from open-source SWE datasets, each instance backed by a per-repo container image.</li><li><strong>Terminal agent (terminal / OS operation).</strong> Multi-step tasks in a live shell, run through the Harbor / <a href="https://www.harborframework.com/docs/agents/terminus-2">Terminus-2</a> agent harness. The model plans a sequence of commands, observes their output, and recovers from errors. Reward is assigned when the task completed successfully. This is the one stage that drives its multi-turn agent loop at the GRPO level, with rollouts spanning up to 64 environment turns.</li><li><strong>Search agent (deep research).</strong> The model answers hard, multi-hop questions using live web-search tool calls inside a browsing agent loop: gather evidence across hops, reason over it, and produce an answer. Because correctness here is open-ended, the reward is an LLM judge on the final answer.</li></ul><h3><a href="https://huggingface.co/blog/ibm-granite/granite-4-2#alignment-rlhf"> </a> Alignment: RLHF</h3><p>The final stage of every model is <strong>RLHF for human preference and safety.</strong> It optimizes against a generative reward model (GenRM) for preference, plus a safety reward covering jailbreak resistance and appropriate refusals. This stage uses the highest KL penalty in the pipeline, aligning tone and safety without eroding the capabilities the earlier stages built. In addition to human preference and safety alignment, this stage also applies a reasoning-length penalty to discourage overly verbose reasoning behavior acquired during earlier stages.</p><h3><a href="https://huggingface.co/blog/ibm-granite/granite-4-2#how-the-three-sizes-differ"> </a> How the Three Sizes Differ</h3><p>Same method and infrastructure; the difference is how far up the ladder each model goes.</p><p>3B is a strong foundational-RL model; 8B and 30B add the agentic-RL block on top, learning to act with tools in real environments.</p><h2><a href="https://huggingface.co/blog/ibm-granite/granite-4-2#agentic-ai-infrastructure-for-scalable-rl"> </a> Agentic AI Infrastructure for Scalable RL</h2><p>Reinforcement learning at this scale needs infrastructure that can drive a training loop and a fleet of live environments at the same time.
