# Async GRPO with LoRA across HF Jobs: a bucket, a proxy, and no NCCL

<h2><a href="https://huggingface.co/blog/asyncgrpo-lora-hfjobs#async-grpo-with-lora-across-hf-jobs-a-bucket-a-proxy-and-no-nccl"> </a> Async GRPO with LoRA across HF Jobs: a bucket, a proxy, and no NCCL</h2><ul><li><code>AsyncGRPOTrainer</code> can now train a LoRA adapter and sync only that adapter to vLLM (TRL v1.14).</li><li>A rank-1 adapter is a few megabytes, so it can travel through a Storage Bucket mounted in every Job instead of over NCCL. The trainer and the vLLM replicas run as separate Hugging Face Jobs on separate machines.</li><li>A small proxy in front of the replicas adds the auth header, routes each rollout to the replica that already holds its KV prefix, and broadcasts adapter loads to every replica.</li><li>The AsyncGRPO metrics show where the bottleneck sits. Five runs take the same recipe from 3 h 27 min to 53 min for 500 steps.</li></ul><p>LoRA support recently landed in TRL&#x27;s <a href="https://huggingface.co/docs/trl/en/async_grpo_trainer"><code>AsyncGRPOTrainer</code></a> with <a href="https://github.com/huggingface/trl/pull/7017">PR #7017</a>, and ships with TRL v1.14. The asynchronous trainer can now train an adapter instead of the full model, and it syncs only the LoRA adapter to vLLM. This post covers a real-world project built on top of it, where training and inference no longer share a machine.</p><p>LoRA training is particularly suited for RL, as shown in Thinking Machines&#x27;s blog <a href="https://thinkingmachines.ai/blog/lora/">LoRA Without Regret</a>. They show that LoRA can match full fine-tuning for policy-gradient RL, even with rank 1. This stems from the fact that the advantage function only gives <code>~O(1)</code> bits of information per episode, so there is not that much to learn from each step, from a total-bits-of-information point of view. A rank-1 adapter has enough capacity to absorb it.</p><p>There is also a systems consequence of LoRA training. A rank-1 adapter for a 1.5B model is a few megabytes, while the full model is around 3 GB. Instead of sending the full policy to the inference workers after every update, we can just send the adapter. vLLM can also keep several adapters loaded at once. Old rollouts finish with the policy they started with, while new rollouts use the latest one.</p><p>TRL&#x27;s <code>AsyncGRPOTrainer</code> already separates training and generation. The trainer and vLLM can run on different machines and at their own speed. This is easy in a single-node or cluster setting where both processes share a filesystem or can form an NCCL group.</p><p>What we want is to run the same setup with <a href="https://huggingface.co/docs/huggingface_hub/guides/jobs">Hugging Face Jobs</a>. Essentially, an HF Job is one container running on one VM. This means that one Job cannot spawn multiple nodes (at least for now) to hold a trainer and a fleet of vLLM servers (we are limited to 8xH200 at most per node). The <code>AsyncGRPOTrainer</code> is built for exactly that kind of scale, so the question became: how far can we get if we drop the requirement that the trainer and the inference servers share a node?</p><p>Well, with a full-weight sync, the answer would be &quot;not far&quot;. Every update would have to move gigabytes between machines, which is what NCCL is for in a dense cluster, but Jobs can&#x27;t communicate <em>across</em> nodes. There is no shared local disk and obviously no shared <code>localhost</code>. With LoRA, a sync is only a few megabytes. For the filesystem part, HF Jobs provide volumes backed by <a href="https://huggingface.co/docs/hub/storage-buckets">Storage Buckets</a>! These buckets can then be mounted as a FUSE filesystem in every Job and are enough to work as a shared FS between nodes. No network path between the Jobs is needed at all.</p><p>The setup ended up being quite small:</p><ul><li>a <strong>trainer Job</strong> running <code>AsyncGRPOTrainer</code> with LoRA (and FSDP, more on that later),</li><li><strong>two vLLM Jobs</strong>, each serving the base model plus whatever adapter the trainer last published,</li><li>a <strong>Storage Bucket</strong> mounted in all three at the same path, which is how the adapter gets from the trainer to the servers,</li><li>a <strong>proxy server</strong>. We&#x27;ll dive deeper into why we need one, but at a high level we need a proxy that routes each rollout to the replica most likely to hold its KV cache, and broadcasts every adapter update to all vLLM replicas.</li></ul><h2><a href="https://huggingface.co/blog/asyncgrpo-lora-hfjobs#the-architecture-leveraging-hugging-face-jobs-and-storage-buckets-🪣"> </a> The architecture: leveraging Hugging Face Jobs and Storage Buckets 🪣</h2><p>The new adapter-only sync path in <code>AsyncGRPOTrainer</code> works like this. The trainer does not send tensors to vLLM. Every few optimizer steps, it saves the adapter under <code>&lt;output_dir&gt;/.vllm_lora/trl-policy-v{N}</code>, publishes the directory with an atomic rename, then sends its path to vLLM&#x27;s <code>/v1/load_lora_adapter</code> endpoint. vLLM loads the files from disk, so the rollout worker can then request <code>model=&quot;trl-policy-v{N}&quot;</code>.</p><p>This is how runtime adapter loading already works in vLLM. The endpoint takes a path, not tensors, so the trainer and the server are expected to share a filesystem. On a Slurm cluster, that is the network filesystem. On Jobs, we get the same thing by mounting a <a href="https://huggingface.co/docs/hub/storage-buckets">Storage Bucket</a> as a volume at the same path in every Job, as we mentioned earlier. Under the hood, it uses <a href="https://github.com/huggingface/hf-mount"><code>hf-mount</code></a>, which exposes the bucket as a POSIX filesystem inside the container:</p><pre>hf jobs run ... -v hf://buckets/aminediroHF/asyncgrpo-lora-buckets:/lora ...</pre><p>Nothing in TRL or vLLM had to change for this. The trainer writes to <code>/lora/&lt;run&gt;/.vllm_lora/</code> and the servers read from the same path. The path sent in the POST request is already valid inside every container.</p><p>Note that we also store the checkpoints and the final adapter in the bucket. The HF Jobs are ephemeral, but a preempted trainer can resume training, as the final adapter is always persisted to the bucket and is never lost when the Job stops.</p><h2><a href="https://huggingface.co/blog/asyncgrpo-lora-hfjobs#the-three-jobs"> </a> The three Jobs</h2><h3><a href="https://huggingface.co/blog/asyncgrpo-lora-hfjobs#the-vllm-replicas"> </a> The vLLM replicas</h3><p>Each replica uses one GPU and the stock <code>vllm/vllm-openai</code> image. We only need to enable <a href="https://docs.vllm.ai/en/latest/features/lora/?h=lora#serving-lora-adapters">runtime LoRA</a> loading and reserve enough adapter slots.</p><pre>for replica in 1 2; do
hf jobs run --detach --flavor h200 --timeout 8h --secrets HF_TOKEN \
    --expose 8000 \
    -v &quot;hf://buckets/${BUCKET}:/lora:ro&quot; \
    -e VLLM_ALLOW_RUNTIME_LORA_UPDATING=1 \
    -e VLLM_SERVER_DEV_MODE=1 \
    -- vllm/vllm-openai:v0.27.1 \
    vllm serve Qwen/Qwen2.5-Math-1.5B --host 0.0.0.0 --port 8000 \
        --max-model-len 4096 --logprobs-mode processed_logprobs --generation-config vllm \
        --enable-lora --max-lora-rank 1 --max-loras 6
done</pre><p>We pin vLLM to <code>v0.27.1</code>. vLLM moves fast, and the flags above and the runtime LoRA endpoints are the ones that version exposes, so treat the version as part of the recipe.</p><p>There is another possible design where the trainer keeps only the latest adapter and always publishes it under the same name. We did not go that way, because vLLM keys its prefix cache by adapter name. With a single name, KV blocks computed under the previous weights would still match after the swap, so the prefill would not be redone and a rollout could get its prefix from one policy version and its decode from the next. The trainer would have no way to tell, and it would show up as <code>ratio</code> drifting away from 1. Versioned names make this impossible: a name always means one set of weights, and a cached prefix can never match a newer version.</p><h3><a href="https://huggingface.co/blog/asyncgrpo-lora-hfjobs#the-dataset-choice-the-sanity-set"> </a> The dataset choice: the Sanity set</h3><p>We chose <a href="https://huggingface.co/datasets/sail/Sanity-Test-R1D-1.5B"><code>sail/Sanity-Test-R1D-1.5B</code></a>, the dataset from <a href="https://huggingface.co/papers/2510.26788">Defeating the Training-Inference Mismatch via FP16</a> (Qi et al., 2025). The reproduction code is in <a href="https://github.com/sail-sg/Precision-RL"><code>sail-sg/Precision-RL</code></a>.</p><p>The authors generated 40 answers for each MATH problem with <a href="https://huggingface.co/deepseek-ai/DeepSeek-R1-Distill-Qwen-1.5B">DeepSeek-R1-Distill-Qwen-1.5B</a>. They kept problems with a success rate between 20% and 80%, yielding 1,460 questions. This dataset is really good for RL validation because the questions are neither already solved nor completely hopeless for that model, meaning the model can get a good early signal to train on and improve.</p><p>This is awesome as a robust end-to-end test: if one vLLM replica silently serves the base model under an adapter name, we want to see that in the curve within a few dozen steps. Also, this dataset is small enough to cycle through in less than two hours.</p><p>We also take the hyperparameters from the paper&#x27;s LoRA scripts in <a href="https://github.com/sail-sg/Precision-RL/tree/main/oat/scripts/lora"><code>oat/scripts/lora</code></a>: <code>Qwen/Qwen2.5-Math-1.5B</code>, LoRA rank 1 with alpha 2, a learning rate of 4e-5, 8 samples per prompt, 128 completions per step, a maximum of 3,000 generated tokens and a 4,096-token context.</p><h3><a href="https://huggingface.co/blog/asyncgrpo-lora-hfjobs#the-trainer"> </a> The trainer</h3><p>The trainer uses the same <code>vllm/vllm-openai:v0.27.1</code> image with TRL installed on top. We ran the PR branch at the time; the same code now ships in TRL v1.14. The training script is a normal <code>AsyncGRPOTrainer</code> script. The only Job-specific values are the output directory and the server URL.</p><pre>from peft import LoraConfig
from trl.experimental.async_grpo import AsyncGRPOConfig, AsyncGRPOTrainer

config = AsyncGRPOConfig(
    output_dir=&quot;/lora/sanity-lora-r1&quot;,
    vllm_server_base_url=&quot;http://localhost:8000&quot;,
    max_staleness=4,
    weight_sync_steps=4,
    save_strategy=&quot;steps&quot;, save_steps=50,
    ...
)
trainer = AsyncGRPOTrainer(
    model=&quot;Qwen/Qwen2.5-Math-1.5B&quot;,
    args=config,
    peft_config=LoraConfig(r=1, lora_alpha=2, target_modules=&quot;all-linear&quot;),
    ...
)</pre><p>During initialization, TRL calls <code>/server_info</code>. If it finds a <code>lora_config</code>, it uses adapter-only sync. Configurations vLLM cannot serve directly, such as DoRA, <code>modules_to_save</code>, or a rank above <code>--max-lora-rank</code>, fall back to merged-weight sync with a warning. The log should contain <code>Adapter-only vLLM sync enabled</code>.</p><h2><a href="https://huggingface.co/blog/asyncgrpo-lora-hfjobs#the-proxy"> </a> The proxy</h2><p>Now onto the fun stuff. We need a proxy between the trainer and the vLLM Jobs for two reasons:</p><ol><p>Exposed Job ports require an <code>Authorization: Bearer &lt;HF token&gt;</code> header on every request. The proxy is where that header gets added, so TRL does not need to know about it.</p></ol><p>We therefore run a small proxy at <code>127.0.0.1:8000</code> on the trainer Job and point TRL to it as if it were a single vLLM server. Besides adding the header, the proxy does two things functionally:</p><ul><li>It sends each completion request to one replica, chosen so that the eight rollouts of a prompt land where their prefix is already cached (details on this below).</li><li>It broadcasts every <em>state-changing</em> request, such as <strong>adapter loads, pause and resume</strong>, to all replicas, so that a policy name means the same thing everywhere.</li></ul><h3><a href="https://huggingface.co/blog/asyncgrpo-lora-hfjobs#routing-rollouts-by-kv-prefix"> </a> Routing rollouts by KV prefix</h3><p>A quick reminder of why this matters. Generating a completion has two phases with very different workload profiles:</p><ul><li>The prefill processes the <strong>whole prompt at once</strong> and computes the attention keys and values for every prompt token.</li><li>The decode phase then produces one token at a time, and each new token attends to the keys and values of all the tokens before it.</li></ul><p>Those keys and values are the KV cache. Because attention is causal, the KV of a token depends only on the tokens before it, not on what comes after. Two requests that share a prefix therefore share the KV of that prefix, and a replica that already has it in cache can <strong>skip that part of the prefill entirely</strong>. The whole game now is to find that replica, so a request can benefit from landing on the replica that has already seen its prefix.</p><p>vLLM stores its <a href="https://github.com/vllm-project/vllm/blob/main/vllm/v1/core/kv_cache_utils.py">prefix KV cache</a> in blocks of 16 tokens. Because of GRPO, the rollout worker sends <code>G</code> requests with the same prompt (in our case <code>G=8</code>). If they all reach the same replica, the first request computes the prefill and the next seven reuse it. With round-robin routing, half would go to a replica that doesn&#x27;t have the prefix cached, and those four requests would redo the prefill work and waste valuable GPU compute.</p><p>The job of <a href="https://github.com/AmineDiro/hfjobs-lora-buckets/blob/main/src/lora_proxy.py">our router</a> is to track which replica has seen which <strong>block hash</strong>. One important detail is that the hashes are chained, so the hash of block 3 represents blocks 1, 2 and 3, not just block 3. This mirrors causal attention: the KV of block 3 is only valid if blocks 1 and 2 are the same too. We also seed the chain with the adapter name because the KV cache also depends on the adapter that generated it: a prefix cached for policy v3 is useless for policy v4!</p><p>The video walks through the entire decision process for choosing a replica. The steps below go through a real 135-token completion request example (from the Sanity dataset problems):</p><p><strong>1. Split the prompt into blocks.</strong> The router receives token ids and cuts them into 16-token blocks, just like vLLM. It only hashes complete blocks, so the last 7 tokens are ignored here.</p><p><strong>2. Hash the prefix.</strong> Each block is hashed with the previous hash, starting from the adapter seed. <code>h3</code> therefore identifies blocks 1, 2 and 3 in order. Two prompts with the same first <code>k</code> blocks get the same hashes up to <code>hk</code>. Once one block changes, every hash after it changes too. This is why we seed the hashes with the adapter name: the same prompt under <code>trl-policy-v4</code> starts from another seed and cannot match entries from <code>v3</code>. This is what we want because the old KV blocks were computed with different weights.</p><p><strong>3. Compare two prompts.</strong> Problem 1 has 103 tokens. Both prompts start with the same 23-token chat template. Their first block is identical, but block 2 already contains the problem text. The hashes differ from there.</p><p><strong>4. Store the owners.</strong> For every hash, the router remembers which replicas served it and which hashes came after it (we cap the successor set at two because we only need to know whether a block has one continuation or several). After a few prompts, the template block <code>h1</code> is owned by both replicas and already has several successors, <code>h2</code> to <code>h8</code> are owned by A only and each has a single successor, and <code>h2&#x27;</code> to <code>h6&#x27;</code> are owned by B only.</p><p>In practice, every prompt in a run starts with the same tokens. Here, it is the chat template and the system prompt, which amount to the first 23 tokens of all 1,460 problems. In an agent setting, it would be the tool descriptions, and in a multi-turn environment it would be the shared conversation history. These blocks are in every replica&#x27;s cache within seconds, so matching on them tells us nothing about where a particular prompt lives.</p><p>A block is <em>common</em> if every replica has served it, or if it has more than one successor. Common blocks are ignored during routing because they do not identify a particular prompt. More on this below!</p><p><strong>5. Pick a replica.</strong> The router counts how many leading blocks match on each replica and removes the common prefix. What is left is the number of blocks specific to this prompt. Then:</p><ul><li>If one replica has specific blocks and it is not swamped, meaning it is at most 8 requests ahead of the least-loaded replica, the request goes there. We call this an <strong>affinity</strong> hit.</li><li>If a replica has specific blocks but it is more than 8 requests ahead, we give up on the cache and send the request to the least-loaded replica. We call this a <strong>spill</strong>.</li><li>If no replica has specific blocks, this is a new prompt. It goes to the least-loaded replica, round-robin on ties. We call this <strong>unmatched</strong>.</li></ul><p>Here is the rule applied to four requests. Start from a state where replicas A and B both have 3 requests in flight, and only the template block <code>h1</code> is known on both replicas.</p><ul><li><strong>Request 1, problem 0, rollout 1.</strong> Both replicas match one block, the template, and that block is common. So nothing specific matches anywhere. The request is unmatched, both replicas are equally loaded, and round-robin sends it to A. The router records <code>h2</code> to <code>h8</code> as owned by A. A now has 4 requests in flight.</li><li><strong>Request 2, problem 0, rollout 2.</strong> Same prompt. A matches all 8 blocks, B matches only the template. After removing the one common block, A has 7 specific blocks and B has none. A is only 1 request ahead of B, well within the limit of 8, so the request goes to A. This is an affinity hit: A already has the whole prompt in its KV cache.</li><li><strong>Request 3, problem 1, rollout 1.</strong> A new prompt. Both replicas match only the template block, so nothing specific matches. The request is unmatched and goes to the least-loaded replica, B, which has 3 in flight against A&#x27;s 5. The router records <code>h2&#x27;</code> to <code>h6&#x27;</code> as owned by B.</li><li><strong>Request 4, problem 0, rollout 9.</strong> Suppose that by now A has 12 requests in flight while B is back to 3. A still has the 7 specific blocks, but it is now 9 requests ahead of B, more than the limit. The request spills to B. B prefills problem 0 once, and the router records <code>h2</code> to <code>h8</code> as owned by B as well. Every replica has now served those blocks, so problem 0 becomes common too, and its later rollouts are placed by load alone.</li></ul><p><strong>6. Reuse the prefill.</strong> Request 2 is the reason for doing all this. It reuses the prefill computed by Request 1: blocks 1 to 8 are already in A&#x27;s KV cache, so A skips straight to decoding the completion. Had it gone to B, B would have prefilled all 135 tokens again while A&#x27;s cache sat unused. Request 3 shows why the <code>common</code> rule is needed. Without it, the shared chat template would make every new prompt look like a cache hit. Request 4 keeps the load bounded. Saving one prefill is not worth letting a replica fall far behind.
